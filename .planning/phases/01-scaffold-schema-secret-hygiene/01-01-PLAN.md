<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer workstation → git remote (GitHub public repo) | Anything committed becomes public; secrets and PII must never cross this boundary |
| npm registry → local filesystem | `npm install` executes `postinstall` scripts (here: `simple-git-hooks` postinstall) — untrusted-by-default code executes at install time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `.env` accidentally committed to public repo | mitigate | `.gitignore` includes `.env`, `.env.local`, `.env.*.local` before the first commit; `.env.example` (committed) documents the pattern without a real value; low-entropy placeholder in .env.example so it does not resemble a real key |
| T-01-02 | Information Disclosure | Real API key checked into `.env.example` by developer error | mitigate | Placeholder is `your_api_key_here` (low-entropy, not `sk-ant-`-shaped) so gitleaks would flag any real-key substitution before commit (secondary defense — gitleaks hook activation is Plan 03) |
| T-01-SC | Tampering | npm `postinstall` script from `simple-git-hooks` package | mitigate | `simple-git-hooks` is [ASSUMED] per RESEARCH.md Package Legitimacy Audit — 1.7k stars, used by PostCSS/Nano ID/VitePress, postinstall writes only to `.git/hooks/`. Plan 03 will introduce a `checkpoint:human-verify gate="blocking-human"` before we rely on the hook for security. In Plan 01, install runs but hook is not yet the security backstop; `.gitignore` is |
| T-01-03 | Tampering | Config file pinning drift (typescript pinned to latest 6.x, could pick up minor changes on future installs) | accept | Ranges are semver-caret; lockfile pins exact resolved versions; risk of accidental minor upgrade breaking the build is low for this well-maintained stack |
</threat_model>
