<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer workstation → public GitHub repo | The entire justification for this plan — any real Anthropic API key or PII that crosses this boundary is an incident requiring immediate revocation |
| gitleaks binary → git working tree | On every commit attempt, gitleaks reads staged files; a compromised gitleaks binary could exfiltrate or falsely allow secrets |
| Homebrew tap → local binary install | `brew install gitleaks` downloads and installs a compiled binary that becomes trusted infrastructure |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-08 | Information Disclosure | Anthropic API key (real) committed to public repo before hook is active | mitigate | Plan 01 committed `.gitignore` (includes `.env`), Plan 02 used low-entropy fixture placeholders, this plan activates the hook and runs a history scan to prove no real key ever landed. Positive control test proves the hook is effective going forward |
| T-01-09 | Information Disclosure | Real personal PII (name, phone, email, address) in fictional fixture data | mitigate | Plan 02 acceptance criteria required fictional identity; this plan runs `gitleaks git` history scan which will not catch PII directly, but the manual review during the human-verify checkpoint is the safety net for PII |
| T-01-SC | Tampering | gitleaks binary (Homebrew) + simple-git-hooks postinstall (npm) | mitigate | Task 1 checkpoint gate="blocking-human" requires manual verification of both packages' legitimacy before install/activation; `simple-git-hooks` postinstall was already accepted at Plan 01 and only writes to `.git/hooks/` per source review |
| T-01-10 | Denial of Service | `biome check --write .` in pre-commit is slow on large working trees | accept | Repo is tiny (~15 files); Biome runs in ms. If it becomes disruptive, switch to `biome check --write --staged` (documented in RESEARCH.md Pitfall 4 as valid alternative) |
| T-01-11 | Elevation of Privilege | A malicious `.gitleaks.toml` allowlist could silently disable Anthropic-key detection | mitigate | Any `.gitleaks.toml` addition in this plan is scoped to `fixtures/.*` paths only (per `<interfaces>` and RESEARCH.md Pattern 5) — never allowlists rule IDs like `anthropic-api-key` globally. Code review of `.gitleaks.toml` at commit time is the enforcement mechanism |
| T-01-12 | Repudiation | Hook silently succeeds without scanning if `gitleaks protect --staged` gets removed in a future version | mitigate | Positive control test at hook-activation time is the direct behavioral proof. If gitleaks upstream ever removes `protect --staged`, the negative control (clean commit) would still pass but the positive control would also pass — the periodic re-test on version upgrade is the mitigation (documented as follow-up for maintenance) |
</threat_model>
